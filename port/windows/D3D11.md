# Direct3D 11 renderer — plan

A second renderer for the Windows build that draws through Direct3D 11
instead of OpenGL. It follows the plan of the Android build's Vulkan renderer
(`port/android/VULKAN.md`), which followed the Switch's deko3d renderer
(`port/switch/DEKO3D.md`): phases, each written out in detail before it is
handed over, each tried on the machine before the next, every result in
"Progress", every phase audited against the source before it is committed.
Read those two plans, and their "Progress", before this one: most of what is
decided here was decided there first, and most of what will go wrong here
went wrong there first. Where this plan differs from them it says so, and
why.

Status: **phase 0 is worked on this PC and committed on `d3d11-backend`**: the probe
(`port/windows/d3d11/win32_d3d11_probe.c`, `ninja windows_d3d11_probe`), its reports on the Adreno and
on WARP, and the OpenGL baseline. The emulated x86 process reaches the Adreno X1-45's own Direct3D 11
driver, at feature level 11_1. The four runs were made again with the debug layer, and the layer
reported nothing, and the agent has seen `present`'s picture through every transition on both
drivers. **Phase 0 is done**: nothing is left for the user. See "Progress". The user decided phase 0's proposals (applied to "Decisions"), and
then the two rows phase 1 depends on (the copies with one shared change; two executables): no row is left to confirm.
**Phase 1 is worked on this PC, committed on `d3d11-backend` and audited**: `ninja windows` makes
`halo.exe` and `halo_d3d11.exe`, whose Direct3D 8 device (cut from `d3d8_gl.c`) draws nothing, whose
backend makes the Direct3D 11 device on the Adreno or WARP, with or without the debug layer, and whose
window has no OpenGL context. It runs the menus and a10's opening into the cryo room with a black
window on both drivers, with no debug-layer message and no GL stub call, and exits clean. The audit
reproduced the object check and found nothing blocking (see "Progress": the audit, the summary and 20
deviations). **Phase 2 is written out below and is next**: the first picture, the game's clears through
Direct3D 11, with the swap chain, the render targets and the diagnostics every later phase relies on.

---

## Why

On Windows the game renders through OpenGL 4.5 (`port/linux/src/d3d8_gl.c`,
the renderer shared with Linux). On Windows that is the second-class API:

- **On Windows on ARM there is no native OpenGL.** The Snapdragon X's Adreno
  GPU has Direct3D 11, Direct3D 12 and Vulkan drivers; OpenGL comes from
  Microsoft's OpenCL and OpenGL Compatibility Pack, which is Mesa's GL
  translated onto Direct3D 12. The game, an x86 executable, already runs
  under emulation there; its graphics then go through a second translation.
  Whatever that layer gets wrong or slow, the game gets wrong or slow.
- **On every other Windows GPU, Direct3D 11 is the driver's first API**: the
  one the driver was written for, tested against and tuned, where OpenGL is
  often a thinner or older path (Intel's integrated GPUs most of all).

So the renderer exists to draw the game on the API every Windows driver
does well, first on Windows on ARM. That decides three things:

- **Correctness first, speed as the result.** Each phase is accepted on what
  it draws, compared with the OpenGL renderer by screenshot, and nothing is
  done for speed alone. Speed is measured once, in phase 7, against OpenGL
  on the same machine: the number that says whether the renderer achieved
  its purpose. The OpenGL renderer's structures that exist for speed (the
  mirror of the game's memory, the state cache, the index extent cache) are
  kept in the copy, because they are proven and free.
- **The test machine is this PC**: a Snapdragon X Plus (Windows 11, Arm64)
  with a Qualcomm Adreno X1-45, running the x86 build under emulation. Every
  phase is tried here, on the GPU and on WARP (below).
- **The OpenGL renderer stays, untouched, selectable for good** and the
  comparison in phase 7 is against it.

Two things this does not assume: that the OpenGL path's faults, if any, are
the translation layer's (some may be in `d3d8_gl.c`'s use of GL, and a
renderer copied from it will carry them: a fault seen on the GPU and on WARP
is ours), and that the emulated x86 process reaches the Adreno's Direct3D 11
driver at all, rather than Microsoft's software adapter. Phase 0's first
question is which adapter the process gets.

## Where the renderer lives

The Windows build compiles two kinds of unit (`tools/windows_build.py`,
`port/windows/README.md`): the game and the Xbox-facing platform units see
the Xbox SDK's headers (`port/include/xdk`), and the Windows-facing units
(`port/windows/src/win32_*.c`) see the Windows SDK's. The two define the
same names differently, so no unit sees both. Direct3D 11 is the Windows
SDK's (`d3d11.h`, `dxgi.h`, `d3dcompiler.h`); the Direct3D 8 device is the
Xbox SDK's (`D3DDevice_*`, `D3DSurface`, `D3D__RenderState`).

So the renderer is split at the draw, as the Vulkan and deko3d renderers
are, but by a header and not by an address space:

- **The device** (`d3d8_d3d11.c`, Xbox SDK): the `D3DDevice_*` entry points,
  the state they keep, the vertex declarations, reading the state back at
  each draw, the shader keys and the HLSL generation, the texture cache and
  decoding, the mirror's bookkeeping.
- **The backend** (`win32_d3d11.c`, Windows SDK): the device, the swap
  chain, buffers, textures, state objects, shaders, queries and draws, as
  plain C functions the device calls at every draw, taking fixed-width
  integers, floats and `const void *` to the game's memory.

The boundary header, `d3d11_backend.h`, includes neither SDK: `<stdint.h>`
and `<stddef.h>` only, so both halves include it. A pointer to the game's
memory crosses it as it is (one process, 32 bits), and the backend copies
what it points at during the call (`UpdateSubresource`, `Map`): nothing of
the game's memory is read later.

Direct3D 11 from C is COM through its C macros (`COBJMACROS`:
`ID3D11Device_CreateBuffer(device, ...)`), which `d3d11.h` supports; the
backend stays C like the rest of the port.

### The platform layer

`sdl_platform.c` (shared with Linux and Android) makes the window with
`SDL_WINDOW_OPENGL`, creates the GL context, loads the GL entry points and
swaps at each present. Under Direct3D 11 there is no host to stand in for
it, so it gains a mode of its own: the window made without `SDL_WINDOW_OPENGL`,
no context, no entry points loaded, no swap: the device's `Present` calls
the backend's present itself (phase 2) and then `platform_video_swap`, which
in this mode only paces (the frame limiter as now; `display.vsync` is the
present's sync interval once there is a present, and the display's refresh
rate as the limiter's interval before that). Behind `_WIN32` and a flag the
Direct3D device sets before it asks for the window, so the OpenGL executable
takes the path it takes today. This is the one change to shared code that
is not an accessor, and the Decisions table says so; phase 1 writes it out.

The GL calls left in shared files the Direct3D executable links
(`hud_hires.c` 7, `text_hires.c` 8, `menu_files.c` 2, `sdl_platform.c` 1,
and `xbox_textures.c`'s 15 until phase 6 replaces it) go to
`gl_functions.c`'s pointers, which are null without a context: a call is a
crash, not a no-op as on Android. The Direct3D executable links a generated
`gl_stubs.c` in its place: every entry point of `gl.h`'s desktop list points
at a stub of its real signature (`__stdcall` on x86: the callee pops the
arguments, so the signature must be right) that counts the call and returns
nothing, and the count is in the statistics line (phase 1), to be zero by
the end of phase 6 as the Vulkan plan's was.

### Clip space, the one place this is simpler

`d3d8_gl.c`'s desktop branch already draws in Direct3D's clip space
(`glClipControl(GL_UPPER_LEFT, GL_ZERO_TO_ONE)`: depth 0 to 1, row 0 at the
top), and its vertex shaders carry Direct3D 8's half-pixel offset (`+ 0.5`),
which Direct3D 11 needs as well (its pixel centres are at half-integers, as
OpenGL's are; the Xbox's were at integers). So the HLSL is the desktop
branch's without a flip, the front face is the desktop branch's, and the
viewport is the game's: none of the orientation questions the Vulkan plan's
phases 4 and 6 had to settle. Phase 6 step 1 checks the picture anyway.

### What Direct3D 11 does not have, checked against the game

- **Point size and point fill.** The game draws no point lists
  (`D3DPT_POINTLIST` and `D3DRS_POINTSIZE` appear nowhere in `source/`) and
  never asks for `D3DFILL_POINT`: `gl_PointSize` and `GL_POINT` go, nothing
  replaces them.
- **Texture view swizzles** (`GL_TEXTURE_SWIZZLE_*` in `xbox_textures.c`:
  Custom Edition caches' channel order, `docs/custom_edition_caches.md`).
  The channels are reordered in the decode instead, where the texels are
  copied anyway (a BC texture whose order is not the Xbox's is decoded to
  BGRA8 and reordered: rare). The Vulkan and deko3d copies solved this for
  their caches (commit `f0218328`); the Direct3D copy does as they do.
- **A blit with scaling** (`glBlitFramebuffer` at present, letterboxed): a
  full-screen draw with a linear sampler. A blit without scaling (the mip
  composite) is `CopySubresourceRegion`.
- **Line width** is 1, as the Vulkan plan found enough. **Logic ops** are not
  used.

Direct3D 11 has, where Vulkan had not: any border colour on a sampler,
exact occlusion counts, `GenerateMips`, and a device that creates resources
and shaders from any thread.

## Phase 0 — spike

A probe, a program of its own built from one Windows-facing unit, that
answers the questions the rest of the plan depends on before any of the
renderer is written, and a baseline: the OpenGL build on this PC, measured
and photographed, which every later phase is compared against. The Vulkan
plan's phase 0 (`port/android/VULKAN.md`, part A, and
`port/android/host/host_vk_probe.c`) is the model: the report format, the
guard that leaves a crashing step out of the next run, the timing rules.
Read that section and that file's head (its first 60 lines, `rep`,
`guard_begin`, `step_table`) first.

Written to be picked up by an agent that has not seen the work so far. The
results go into "Progress" before phase 1 starts; the probe stays in the
tree as the way a tester's machine is reported later (phase 7).

### What this phase is, and is not

- **It is** the probe (`port/windows/d3d11/win32_d3d11_probe.c`), the build
  changes that make it (`build/windows/d3d11_probe.exe`), its reports for
  the Adreno and for WARP in `port/windows/probe/reports/`, and the
  baseline's numbers and pictures.
- **It is not** the renderer. No file under `port/linux/src` changes. No
  Direct3D 8 device, no `halo_d3d11.exe`, no setting in `config.toml`. The
  probe is written to measure, not to be the backend: phase 2 may copy
  pieces (the swap chain's handling, the adapter choice) once they are
  proven here.
- **The OpenGL build does not change.** Its executable is built here only
  to be measured.

### The probe's shape

- **A program**, not a mode of the game: `d3d11_probe.exe [steps]
  [--adapter hardware|warp|<part of a name>] [--shaders <folder>]
  [--report <file>] [--sync 0|1]`. `steps` is `all` (the default) or a
  comma list of `caps,present,compile,memory,queries`, run in that order
  whatever order they are written in. `caps` always runs, because every
  step needs what it finds (the Vulkan probe's deviation 7).
- **Windows-facing.** The unit sees the Windows SDK only (`<windows.h>`,
  `<d3d11.h>`, `<dxgi1_6.h>`, `<d3dcompiler.h>`, `<SDL3/SDL.h>`) with
  `COBJMACROS` and `WIN32_LEAN_AND_MEAN`, so it is compiled with the build's
  `WIN32_FLAGS` like `win32_*.c` is. C, `-std=gnu11`, as the rest of the
  port. Whatever else the headers need to compile under clang's
  `i686-pc-windows-msvc` target (a define, a warning silenced) is written
  into "Progress" as the build's first finding: phase 1's backend is
  compiled the same way.
- **The report.** Every result is a line `section.key: value`, one fact
  each, written to the report file (default `d3d11_probe.txt` in the
  current directory; `--report` names another) and to standard output with
  the prefix `d3d11 probe:`. The file is opened at the start and flushed
  after every line. The first lines: the build (the git hash and
  `+changes` if the tree is dirty, taken at build time into
  `build/windows/d3d11_probe_build.h` by a small generated header, as the
  Android build's `tools/android_build_stamp.py` does; copy its approach),
  the machine (`GetNativeSystemInfo`'s architecture, `IsWow64Process2`'s
  native and process machines: the process is x86 under an Arm64 host
  here, and the report must say so), the OS version (`RtlGetVersion`), the
  steps asked for and the adapter asked for.
- **The guard.** A step, or a risky sub-step, writes its name to
  `d3d11_probe_running.txt` beside the report before it runs and clears it
  after; a run that finds the file at start appends that name to
  `d3d11_probe_skip.txt`, says so in the report (`guard.<name>: skipped (it
  killed the probe once; delete d3d11_probe_skip.txt to try again)`) and
  leaves it out. The Vulkan probe's `guard_begin`/`guard_end` with its
  part-B fix (`guard_end` restores the step's own name, not nothing).
- **Errors.** Every `HRESULT` that is not `S_OK` is reported with its hex
  value and, where DXGI or the device has one, its name (a small table of
  the common ones: `DXGI_ERROR_DEVICE_REMOVED`, `E_INVALIDARG`,
  `DXGI_ERROR_UNSUPPORTED`, `DXGI_ERROR_NOT_FOUND`, `E_OUTOFMEMORY`). A
  step that fails reports `step.<name>: failed (<where>, <hresult>)` and
  the next step runs. Nothing is called through a null interface.
- **The debug layer.** The device is made with `D3D11_CREATE_DEVICE_DEBUG`
  first; if that fails with `DXGI_ERROR_SDK_COMPONENT_MISSING` (the
  Graphics Tools feature is not installed) it is made without, and the
  report says which (`debug_layer: yes|no (<hresult>)`). With the layer,
  the `ID3D11InfoQueue` is read after every step and every message is
  reported (`debug.message: <severity> <id> <text>`), with a count at the
  end; a step whose messages name a mistake in the probe is fixed, not
  explained away.
- **Timing** is `QueryPerformanceCounter` for wall time and
  `GetThreadTimes` for one thread's CPU time; GPU time where a step asks
  for it is a `D3D11_QUERY_TIMESTAMP_DISJOINT` pair. Every timing is
  several runs: the first on its own, then the minimum and median of the
  rest.
- **The adapter.** `--adapter hardware` (the default) takes the first
  adapter `IDXGIFactory6::EnumAdapterByGpuPreference` lists for high
  performance that is not the software adapter, or the first adapter at
  all if that interface is missing; `warp` is `D3D_DRIVER_TYPE_WARP`; a
  name takes the first adapter whose description contains it. Feature
  levels asked for: 11_1, 11_0, 10_1, 10_0 in that order, so the report can
  say what the adapter offers even below the plan's minimum.
- **When it ends**, every object is released in reverse order (with the
  layer on, `ReportLiveDeviceObjects` with `D3D11_RLDO_SUMMARY` says
  whether anything leaked; the count goes into the report), the report says
  `probe.done: yes`, and the program exits 0; a failed step makes it exit 1.

- The build stamp header above, generated by a rule of its own so it is
  written at every build (the Vulkan probe's lesson: a stamp taken at
  configure time goes stale).

### Step 0: the baseline (the OpenGL build on this PC)

Not a probe step. The number and the pictures every later phase is held
against.

1. `python configure.py --portable --release` and `ninja windows`: the

### Step 2: a frame on the screen (`present`)

Run last, because it waits for the tester. What phase 2's present will be:

- An SDL3 window (`SDL_CreateWindow` with `SDL_WINDOW_RESIZABLE |
  SDL_WINDOW_HIGH_PIXEL_DENSITY`, **without `SDL_WINDOW_OPENGL`**), its
  `HWND` from `SDL_GetPointerProperty(SDL_GetWindowProperties(window),
  SDL_PROP_WINDOW_WIN32_HWND_POINTER, NULL)`; a swap chain on it from
  `IDXGIFactory2::CreateSwapChainForHwnd`: `DXGI_SWAP_EFFECT_FLIP_DISCARD`,
  two buffers, `B8G8R8A8_UNORM`, `DXGI_SCALING_NONE`, no MSAA; then
  `MakeWindowAssociation(hwnd, DXGI_MWA_NO_ALT_ENTER |
  DXGI_MWA_NO_WINDOW_CHANGES)` so DXGI leaves the window to SDL. Each frame
  clears the back buffer to a colour that cycles over a few seconds, draws
  a small built-in triangle over it (a vertex and pixel shader compiled
  with `D3DCompile` at the start: the step's own proof that the compiler is
  reachable from this process) and presents with the sync interval
  `--sync` gives (1 by default; the step is run twice, 1 then 0).
- **Resizing and modes.** On `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED` the
  back buffer's view is released and `ResizeBuffers(0, 0, 0,
  DXGI_FORMAT_UNKNOWN, 0)` is called; every resize is logged with the new
  size and the result. The tester's script (below) resizes, makes the
  window fullscreen both of SDL's ways (`SDL_SetWindowFullscreen` with a
  NULL mode: borderless; and with the display's current mode: exclusive),
  restores it, minimises and restores, and presses Alt+Enter (nothing
  should happen). Each transition: did presenting go on, did `Present`
  return anything but `S_OK` (`DXGI_STATUS_OCCLUDED` while minimised is
  expected; what else?), how long the transition took.
- **Pacing**: the interval between presents measured at the CPU after
  `Present` returns: minimum, median, maximum and the count more than 1.5
  times the median, over each ten seconds; the display's refresh rate
  beside it (`SDL_GetCurrentDisplayMode`). With `--sync 1` it should be the
  refresh; with `--sync 0` whatever the GPU gives. Also
  `DXGI_PRESENT_ALLOW_TEARING` with sync 0 if the factory says it is
  supported (`CheckFeatureSupport(DXGI_FEATURE_PRESENT_ALLOW_TEARING)`):
  supported or not goes into the report.
- **SDL beside Direct3D**: the first gamepad opened and every button press
  logged by name; keyboard events logged; a one-second tone through an SDL
  audio stream when the step starts.
- **The tester's script**, printed when the step starts: watch the colour
  cycle; resize the window by its edge; press F11 (the probe toggles
  borderless), F10 (exclusive), Escape (windowed); F9 cycles three window
  sizes; minimise and restore; Alt+Enter; A on a gamepad or Enter if the
  picture looks right, Y or Backspace if not, B or Escape twice to end.
  With no input for 120 seconds the step ends on its own and says so. The
  agent can run this step itself by sending the keys to the window
  (PowerShell's `SendKeys` after `AppActivate`) where the user is not there
  to; the user does it once by hand before the phase is accepted.

### Step 3: the shader compiler (`compile`)

**Which shaders.** From step 0's dump: the largest vertex shader, the
largest pixel shader (most texture stages and combiner stages), and a
typical one of each (the median size). Convert each to HLSL by hand,
changing only what HLSL needs and keeping the bodies: `#version` and
`precision` gone; the loose uniforms into one `cbuffer` per stage with
every member a `float4` or an array of them (`c[192]` stays `float4
c[192]`); `in`/`out` into a struct of `TEXCOORDn` semantics with
`SV_Position`; `texture()` into `Texture2D` with a `SamplerState` and
`Sample`; `mix`, `fract`, `mod` into `lerp`, `frac`, `fmod`; `discard`
stays. Add a trivial pair (a pass-through) for the fixed cost. Commit them
under `port/windows/probe/` with a comment at the top of each naming the
dump file it came from and the build that made it. This conversion is not
phase 4: it is four shaders by hand, to time the compiler on shaders of the
right size.

**What is measured**, for each shader (`--shaders` names the folder; the
committed folder by default), ten times: `D3DCompile` with the target
`vs_4_0` or `ps_4_0`, `D3DCOMPILE_OPTIMIZATION_LEVEL3`, no debug; then
`CreateVertexShader` or `CreatePixelShader` from the blob. The first
compile of the first shader on its own (it pays the DLL's load), then per
shader the minimum and median of the rest, wall and thread CPU time, and
the bytecode's size. Then the same shaders at `vs_5_0`/`ps_5_0`, for the
difference in time and size. And whether `precise` on the position output
compiles for `vs_4_0` (the `invariant gl_Position` the generators need;
`D3DCOMPILE_IEEE_STRICTNESS` is the fallback to try if not). Every blob is
written to `d3d11_probe_shaders\` beside the report, so it can be looked at
with `D3DDisassemble` later.

The numbers decide Decisions' "compiled at the draw, synchronously": a
game-sized shader at a few milliseconds is what GLSL costs today; at tens
of milliseconds phase 5 adds the compile thread.

### Step 4: buffers (`memory`)

The costs the renderer pays every frame, and the proof that a copy is
made when the call is made:

1. **The stream ring**: a `D3D11_USAGE_DYNAMIC` vertex buffer of 32 MB
   (the OpenGL build's `STREAM_BUFFER_SIZE`), written with `Map`
   `D3D11_MAP_WRITE_NO_OVERWRITE` in 64 KB pieces, 4 MB a frame, `DISCARD`
   at the wrap, 300 frames with a draw from each piece into an offscreen
   16×16 target: CPU time of the maps and copies per frame (minimum,
   median), GPU time of the frame.
2. **The mirror's segment**: a `D3D11_USAGE_DEFAULT` buffer of 4 MB
   updated with `UpdateSubresource` in 4 KB pieces (a page), 1,024 pieces a
   frame (the whole segment) and then 64 a frame (a quiet frame's stale
   pages), 300 frames each, drawn from each frame: the same timings. And
   once with a `D3D11_USAGE_STAGING` buffer plus `CopySubresourceRegion`
   for the comparison.
3. **Rewrite seen.** A buffer of three vertices written red and drawn,
   rewritten green through the same path and drawn again in the same
   frame, both draws into their own target, read back through a staging
   texture: the first must be red and the second green, for the ring's
   path and the mirror's path. This is the Vulkan plan's data self-test,
   run before the renderer exists.
4. **A texture by `UpdateSubresource`**: a 512×512 BC1 texture's level 0,
   and the same as BGRA8, 300 times: the time per upload. And a 2,048×2,048
   BGRA8 once (a high-res HUD bitmap's size).
5. **The address space** after 64 MB of buffers are alive
   (`GlobalMemoryStatusEx`), reported with step 1's figures.

### Step 5: queries (`queries`)

- 64 `D3D11_QUERY_OCCLUSION` queries, each around a draw of a known
  coverage (a square of n×n pixels into a 256×256 target), ended, and
  `GetData` with `D3D11_ASYNC_GETDATA_DONOTFLUSH` polled once a frame,
  never waited on: how many frames until each answers (minimum, median,
  maximum) and whether the count is exactly n², on the GPU and on WARP.
  Then the same with `Flush` after the end of the frame, for the
  difference. And `D3D11_QUERY_OCCLUSION_PREDICATE` for the record.
- 4,096 queries made at once (the game's slots): creation time and whether
  the device objects.

### The device: `d3d8_d3d11.c`

A copy of `d3d8_gl.c` (4,897 lines, 239 GL calls, 61 conditionals all on
`HALO_ANDROID`) made in this order, so the audit can follow it:

1. **Copy the file whole** and write its header: what it is, the commit of
   `d3d8_gl.c` it was copied from (`git log -1 --format=%h --
   port/linux/src/d3d8_gl.c`), and that changes to `d3d8_gl.c` are not
   followed automatically. Later phases copy decisions from `d3d8_gl.c` as
   it is then, and say in "Progress" if the copy already holds an older one
   (the Vulkan plan's rule).
2. **Take the desktop side of every `HALO_ANDROID` conditional** (the
   `#else` and `#ifndef` sides; the desktop branch has no macro of its own)
   and drop the Android side, the ES shims (`d3d8_gl.c` 56–74) and
   `xgpu_capabilities`, which only Android declares.
3. **Take out every GL call** (`\bgl[A-Z]\w+\(` finds them; the audit greps
   for zero) and what exists only to make them. What goes:
   the GL state cache, the program and fragment caches and `program_*`,
   the samplers, the render targets' GL side (`render_target_*`, the
   framebuffer cache, resolve, the mip composite), multisampling, the
   anti-aliasing passes and `xgpu_post_*` calls, the mirror's GL buffers
   and the stream and index rings' GL side, `write_screenshot`, the query
   buffers, `gl_initialize`'s GL queries of limits, the pointer's GL draw,
   and the tracing that prints GL names. **What stays, as it is**: the
   screen's width and scale and everything `halo_screen_*` exports; the
   `D3D__*` arrays and every `SetRenderState_*`/`SetTextureState_*`; the
   transforms, the viewport and its reserved constants; the vertex shaders
   and their declarations (`struct vertex_element`), `CreateVertexShader`
   through `SetVertexShaderConstant`; `SetStreamSource`, `SetIndices`;
   immediate mode's accumulation (`Begin`, `SetVertexData*`, `End`); the
   surfaces and render targets *as the game sees them* (`SetRenderTarget`,
   `GetBackBuffer`, `GetDepthStencilSurface`, the back and depth buffers
   from `d3d8_surface_initialize`); `GetDeviceCaps`'s constant answer; the
   vertical blank thread, `flip_count`, `pending_flips`, `d3d_find_flipcount`,
   `SetVerticalBlankCallback`, `BlockUntilVerticalBlank`; `InsertCallback`;
   the debugging settings; the statistics; and every function another
   object calls (the table in "The link is the check", below).
4. **What drew, cleared or uploaded keeps its state and returns**:
   `DrawVertices`, `DrawIndexedVertices` and `End`'s draw count the draw
   in `stats` and return; `Clear` counts; `SetTexture`, `SetPalette`,
   `SetPixelShaderProgram` keep the pointer or the program; `LoadVertexShader`
   and `SelectVertexShader` keep what they keep now; `SetRenderTarget` keeps
   the surfaces. Nothing is uploaded, so `xgpu_texture_get` and
   `xgpu_texture_cache_begin_frame` are not called (phase 6's work).
5. **The answers the game reads back** are the OpenGL build's where they do
   not depend on the GPU, which is all of them but one: `IsBusy` is `FALSE`
   as now, `KickPushBuffer` is empty, `InsertCallback` calls at once,
   `GetDeviceCaps` answers the same constants, `GetBackBuffer` returns the
   same surface, `PersistDisplay` returns `S_OK`, the locks are
   `d3d8_resources.c`'s and return pointers into the game's memory as now.
   The one that depends on the GPU, `GetVisibilityTestResult`, returns 0
   samples and `S_OK` with `time_stamp` 0 (never `D3DERR_TESTINCOMPLETE`),
   until phase 6 step 6 counts: lens flares stay dark (the Vulkan plan's
   phase 1 saw a lens-flare warning in the log that its GL build logs
   too; if this build logs one, "Progress" says so).
6. **Device creation** (`Direct3D_CreateDevice`, `d3d8_gl.c` 1734–1812) keeps
   its initialisation of the device's state, then, where it calls
   `platform_video_initialize` and `gl_initialize`:

     still skips the window, with the same log line.
   - `d3d11_backend_create(adapter, debug, line, size)` with
     `display.d3d11_adapter`'s string and `debug.d3d11_debug`'s boolean; the
     line it returns is logged with `platform_log`, whatever it says. The
     device's `backend_ready` is its result: with 0 the game runs with a
     window and no picture, as `debug.null_renderer` does today, and the
     player's way back is `halo.exe`.
   - `memory_watch_initialize()`, where `gl_initialize` calls it (1601):
     **this is the call the Vulkan cut lost.** Nothing uses the watch in
     phase 1, but phase 3's mirror and phase 6's textures expect it running

7. **`Present`** (`d3d8_gl.c` 4771–4894) keeps: the frame count, the
   statistics line (its form in this phase, below), `platform_pump_events`,
   and the vertical blank block as it is (two frames queued without
   interpolation, `flip_count` with it). It calls `platform_video_swap()`
   where the OpenGL one does, after the blit it no longer has: in the
   no-context mode that call paces the frame (below) and presents nothing.
   `debug.screenshot_every` is read and, if set, logged once as not
   available until phase 2.
8. **The exports the shared files call** stay defined:
   `xgpu_gl_state_invalidate` as an empty function (`xbox_textures.c`,
   `hud_hires.c` and `text_hires.c` call it); `halo_ui_pointer_update` and
   `halo_scoreboard_pointer_update` as the desktop versions with their GL
   draw taken out; `d3d8_renderer_description` answering `"Direct3D 11"`
   where it answers `"OpenGL"` now (`menu_functions.c` prints it). `xgpu_compile_shader`, `xgpu_link_program` and

### The backend: `win32_d3d11.c` and `d3d11_backend.h`

The first Windows-facing unit of the renderer, compiled as `win32_*.c` is
(`WIN32_FLAGS`, no prefix header, no Xbox SDK; `COBJMACROS`;
`d3d11_4.h`, `d3d11sdklayers.h`, `dxgi1_6.h`; phase 0's build finding:
nothing else is needed, and `INTERFACE` must not be defined by the unit).
It copies from the probe, and says so in its header, the adapter choice
(`choose_adapter`), the device creation with the debug layer's fallback
(`create_device`), `hr_text` and `drain_debug`: the pieces phase 0 proved.
What it does not copy: the probe's report, guard, timing and steps.

`d3d11_backend.h` includes `<stdint.h>` and `<stddef.h>` only, so
`d3d8_d3d11.c` (Xbox SDK) and `win32_d3d11.c` (Windows SDK) both include it.
Its functions take and return fixed-width integers, `int`, `const char *`
and `void *`; nothing of either SDK's types crosses, as `update.h` and
`posix.h` already do between the two worlds. In this phase:

- `int d3d11_backend_create(const char *adapter, int debug_layer, char
  *line, size_t line_size)`: 1 with a device, 0 without; `line` filled
  either way (the one log line, below). `adapter` is `display.d3d11_adapter`:
  empty for the first hardware adapter `IDXGIFactory6::EnumAdapterByGpuPreference`
  lists for high performance that is not software (the first adapter at all
  without that interface); `"warp"` for `D3D_DRIVER_TYPE_WARP`; anything
  else, the first adapter whose description contains it, case-insensitively,
  and **if none does, the first hardware adapter, and the line says the
  name matched nothing** (the probe failed instead; the game has a window
  to keep). `D3D11CreateDevice` asks for 11_1 then 11_0, and no lower:
  **11_0 is required** (Decisions), so a machine below it gets no device
  and the line says what level it offered (ask once more with 10_1 and
  10_0 only to name it, then release it). Flags:
  `D3D11_CREATE_DEVICE_BGRA_SUPPORT` always (the swap chain's format in
  phase 2), `D3D11_CREATE_DEVICE_DEBUG` when `debug_layer` is set, falling
  back without it on `DXGI_ERROR_SDK_COMPONENT_MISSING` and saying so in
  the line. Kept in the unit's static state: the factory, the adapter, the
  device (`ID3D11Device`), the immediate context, the feature level, the
  `ID3D11InfoQueue` when the layer is on (its storage limit raised as the
  probe's), the adapter's description and driver version
  (`CheckInterfaceSupport` with `IID_IDXGIDevice`, as the probe reads it).
  Nothing is made that phase 2 would make again.
- `uint32_t d3d11_backend_drain_debug(void)`: every stored message of the
  info queue to the log as `d3d11 debug: <severity> <id> <text>`, cleared,
  the count returned; 0 at once without the layer. The device calls it from
  `Present` every frame (cheap with nothing stored), so a message is seen
  in the frame it was made.
- `void d3d11_backend_destroy(void)`: with the layer,
  `ReportLiveDeviceObjects(D3D11_RLDO_SUMMARY)` and the count of its
  messages to the log (phase 0 saw 9 for the device's own objects); then
  every object released in reverse order. Called from `D3DDevice_Release`
  if the game reaches it, and from an `atexit` handler registered at
  creation otherwise, so the layer's report is seen on a normal exit.
- The log: the backend declares `void platform_log(const char *, ...)` by
  hand, as `win32_memory_watch.c` does, for `drain_debug` and `destroy`;
  the creation line is returned, not logged, so the device logs one line
  in one place (the Vulkan plan's deviation 2).

**The one log line**, either way:

```
renderer: Direct3D 11 on Qualcomm(R) Adreno(TM) X1-45 GPU, feature level 11_1, driver 31.0.137.0, debug layer off
```

### The GL stubs

The shared files the Direct3D executable links still call GL:
`hud_hires.c` (7 calls in `hud_hires_png_texture`), `text_hires.c` (8 in
`text_hires_atlas_texture`), `menu_files.c` (2 `glDeleteTextures`),
`xbox_textures.c` (15, in the texture cache the device does not call in
this phase) and `sdl_platform.c` (1, not reached in the no-context mode).
They go through `gl.h`'s `halo_gl*` pointers, which
`gl_functions.c` defines and loads; without a context they are null, so a
call is a crash. The Direct3D executable leaves `gl_functions.o` out and
links `gl_stubs.o` in its place, generated because every stub needs the
function's real signature: GL's entry points are `APIENTRY` (`__stdcall`
on x86), where the callee pops the arguments, so a stub of the wrong
signature corrupts the stack.

- **`tools/windows_gl_stubs.py gl.h SDL_opengl.h SDL_opengl_glext.h
  output.c`**, modelled on `tools/android_gl_stubs.py`: the function list is
  the desktop `GL_FUNCTIONS(X)` of `gl.h` (the one after the
  `ANDROID_GL_FUNCTIONS_END` marker; 114 names), the prototypes from SDL's
  headers (`GLAPI <return> APIENTRY <name> (<parameters>);` in
  `SDL_opengl_glext.h`, and `GLAPIENTRY` in `SDL_opengl.h` for the 1.1
  functions such as `glGetString`); a name with no prototype fails the
  generation, loudly. For each: `static <return>
  APIENTRY stub_<name>(<parameters>) { gl_stub_called(<index>,
  __builtin_return_address(0)); return 0; }` (nothing for `void`, NULL for
  pointers), and `__typeof__(&<name>) halo_<name> = stub_<name>;`, the
  definition `gl.h` declares `extern` (compiled with `GL_FUNCTIONS_DEFINE`
  as `gl_functions.c` is). **The stubs write no output parameter**: a
  `glGenTextures` leaves the name 0, a `glGetIntegerv` leaves the value
  as it was. Phase 6 replaces each caller through the accessors the files
  already have (`hud_hires_png_pixels`, `text_hires_atlas_rows`,
  `menu_art_*`), as the Vulkan plan did.
- **The count**: `gl_stub_called` keeps a count per function and the first
  caller's return address; `unsigned long gl_stubs_calls(void)` returns the
  total for the statistics line, and the first call of each function logs
  once `gl stub: <name> called from <address>`, symbolised by hand from
  `halo_d3d11.pdb` (`llvm-symbolizer --obj=build/windows/halo_d3d11.exe
  <address>`). The Vulkan plan counted 0 of 102 in the menus, because the
  shared files' GL calls are reached only through `d3d8_gl.c`; here the
  expectation is the same, and `menu_files.c`'s `glDeleteTextures` on a
  replaced menu art is the likely exception. "Progress" lists what was
  counted, so phase 6 knows.
- A self-test at creation, as the Vulkan plan's: the device calls one stub
  (`glFlush`, through the pointer) and checks the count moved, logging
  `gl stubs: self-test ok` or failing creation loudly.
- The generated file compiles as `gl_functions.c` does (`platform_cflags`:
  it includes `gl.h`, and through it SDL's GL headers), with the generator
  and `gl.h` as the rule's implicit inputs.

## Phase 2 — the backend's skeleton

The first picture: the game's clears, through Direct3D 11, on the screen.
The Vulkan plan's phase 2 (`port/android/VULKAN.md`, "Phase 2 — the
backend's skeleton", and its "Progress" entries for phase 2: the audit, the
summary, the deviations) is the model, less its command stream: here the
device calls the backend directly, and the backend records nothing for
later. Phase 0's `present` step (`win32_d3d11_probe.c`, `step_present`) is
the swap chain's proof on this PC and the code the backend copies for it.
Three of the Vulkan phase's lessons are built into this one: a clear of some
channels only cannot be a clear call and is drawn (its deviation 10 added a
self-test for it, which is in this phase from the start); the marker is
drawn, not cleared, and sits on the picture after the blit (its deviation
2); and "target changes" counts a pair that differs from the last, not each
rebinding (its deviation 11).

Written to be picked up by an agent that has not seen the work so far. The
source facts it relies on (line numbers in `d3d8_gl.c`, `d3d8_d3d11.c`,
`win32_d3d11.c`, `sdl_platform.c`, `win32_d3d11_probe.c`) are from
`d3d11-backend` at `d943c612`; `d3d8_gl.c` is still at `2765d816`, the
commit the device was copied from. Read the files, not the numbers, if they
have moved.

### What this phase is, and is not

- **It is** the swap chain on the game's window; the game's render targets
  as Direct3D 11 textures, found by the surface they stand for; the game's
  clears, through clear calls where they can be and drawn where they cannot;
  the back buffer presented by a letterboxed draw into the swap chain's
  buffer, with `display.vsync` as the sync interval; the window's resizes
  and modes followed; the diagnostics every later phase relies on (the
  statistics, the debug layer's messages in the frame they are made, a lost
  device as a log line, screenshots, the marker, a clears' self-test).
- **It is not** drawing: no vertex data, no shaders of the game, no
  textures, no multisampling, no anti-aliasing passes (phases 3 to 6). The
  menus show as their clears, plain colours, black for most of them; a map
  shows its sky's clear and its fog's. Draws and immediate-mode draws are
  still counted and dropped, as phase 1 left them.
- **`halo.exe` does not change in what it does**, and this time neither do
  its objects: the two settings rows are the only change under
  `port/linux/src` (the no-context mode gains nothing), so the object check
  of phase 1 holds with `port_config.o` as the one difference (and the
  harmless checksum and time differences phase 1's "Progress" lists).
- **Nothing is copied that this phase does not need.** `xbox_textures.c`,
  `nv2a_vsh.c`, `nv2a_psh.c` and `xgpu_post.c` stay out, as phase 1 left
  them.

   `struct render_target_entry`, the buckets, `surface_dimensions`,
   `surface_is_shadow_map`, the recent-targets cache, `render_target_remember`,
   `render_target_get`) copied as it is, with `struct xgpu_render_target`'s
   GL members unused and one member added, the backend's handle (`uint32_t
   backend_target`, 0 while none). The key is `d3d8_gl.c`'s: the surface's
   `Data`, its width and height in the game's units, whether it is a depth
   surface, and its scale (the screen's for the screen's targets, the shadow
   maps' for those, 1 otherwise); its pixel size is `gl_width` and
   `gl_height`, computed as now (`width * scale + 0.5`). Where
   `render_target_get` made the GL texture (1231–1239) it calls
   `d3d11_backend_target_create(gl_width, gl_height, depth)` and keeps the
   handle; a handle of 0 (the backend could not make it) leaves the entry
   with none, logged once per entry, and every use of that entry is skipped.
   The entries are never freed, as now; the statistics say how many exist.
   `recent_render_targets` is forgotten where `halo_screen_commit` forgets it
   (phase 1 left that line out: it comes back). `xgpu_render_target_find`
   stays undefined (its callers are `xgpu_post.c` and the hosts).
2. **`bind_targets`** (1432–1479) copied without multisampling (the
   `samples`, `render_target_multisample` and `renderbuffers` lines; phase 6
   brings them): the colour and depth entries looked up, `last_rendered`
   and `written` kept, `target_scale` set from the colour target's scale
   (or the depth's), and `d3d11_backend_targets_set(color_handle,
   depth_handle)` where it bound the framebuffer. A depth entry that is not
   a depth surface is dropped as now. Called from `Clear` and, from phase 6,
   from every draw; `SetRenderTarget` itself stays as phase 1 has it (it
   keeps the surfaces and resets the viewport; the binding happens at the
   clear or the draw, as in `d3d8_gl.c`).
3. **`Clear`** (4614–4689) copied with its arithmetic whole and its GL
   lines replaced: `bind_targets` first (nothing to clear into: return, as
   now); the trace line and the count as phase 1 has them; then the
   rectangles **in the targets' pixels, as `d3d8_gl.c` works them out**: a
   clear without rectangles is the viewport's rectangle (`target_pixel` of
   its corners, `scaled_pixel` copied with it: `floor(coordinate * scale +
   0.5)`); rectangles are clipped to the viewport, moved right by
   `UI_OFFSET`, and empty ones skipped. One call,
   `d3d11_backend_clear(channels, color[4], z, stencil, rectangles, count)`,
   with `channels` the flags' `D3DCLEAR_TARGET_R/G/B/A` bits and the depth
   and stencil bits (`D3DCLEAR_ZBUFFER`, `D3DCLEAR_STENCIL`, dropped when
   there is no depth target, as `has_depth` drops them now), the colour from
   `color_to_vec4`, and the rectangles as `{x, y, width, height}` in pixels
   with row 0 at the top. `d3d8_gl.c`'s GL rectangles were the other way up
   (`glScissor` counts from the bottom); Direct3D's are not, so **no flip**:
   `y` is `target_pixel(top, 1)`, as the Vulkan plan did. The device does not
   know or care whether the backend clears or draws; the backend's answer
   (how it cleared) goes into the statistics (below).
4. **`Present`** (phase 1's, `d3d8_d3d11.c` 1498): where `d3d8_gl.c`'s
   resolved and blitted the back buffer (the block from `render_target_resolve` to `glBlitFramebuffer`, after 4771), the device looks the
   back buffer up (`render_target_get(&device.back_buffer)`, its entry made
   now if the game cleared nothing into it yet, so a frame with no clear
   still presents black) and calls `d3d11_backend_present(handle,
   window_pixel_width, window_pixel_height, sync_interval)` with the
   window's size from `platform_video_drawable_size` (the resize is found
   there, below) and `display.vsync` as 1 or 0, read as `frame_interval_ns`
   reads it (when `config_changes()` moves). The result says whether a
   picture was presented (1), nothing was (0: the window is minimised or
   occluded, or there is no swap chain), or the device is lost (-1, below).
   Then the pacing: **`platform_video_swap()` is called when the present
   did not pace the frame**, that is when the result is not 1, or when
   `display.vsync` is off (the frame limiter of `display.max_fps` as now);
   with vsync on and a presented frame, the sync interval paced it and
   `platform_video_swap` is not called (the stand-in refresh-rate interval
   phase 1 put in `sdl_platform.c` stays, and is what paces a frame nothing
   presents, so a minimised game does not spin). The frame count, the
   statistics, `platform_pump_events` and the vertical blank block stay as
   they are. `debug.screenshot_every`'s line of phase 1 goes; the screenshot
   is below.
5. **The device lost.** A result of -1 from `present`, or 0 from
   `target_create` after the backend reported the device lost, sets
   `backend_ready` false and logs once `Direct3D 11: the device was lost
   (<reason>); the game goes on without a picture`, with the reason the
   backend logged from `GetDeviceRemovedReason`. From then on `Clear` and
   `Present` keep their counts and call the backend no more (the
   `backend_ready` checks phase 1 put at the visibility tests are the
   pattern); `platform_video_swap` paces every frame. Not a crash, and not
   a new device: the player's way back is `halo.exe`.
6. **Screenshots** (`debug.screenshot_every`, `debug.screenshot_directory`):
   `write_screenshot` (4722–4769) copied, its `glReadPixels` replaced by
   `d3d11_backend_target_read(handle, pixels, size)`, which fills BGRA rows
   from the top; alpha forced to 0xff and the BMP written as now, at the
   target's pixel size, `frame%05lu.bmp`. Called from `Present` before the
   present, as now.
7. **`ui_point_from_window_on`** goes back to `d3d8_gl.c`'s form (the entry
   from `render_target_get`, its `gl_width` and `gl_height`); phase 1's
   `back_buffer_pixels` goes.
8. **The clears' self-test** (`debug.d3d11_self_test`): once, at creation
   after the backend's line, `d3d11_backend_self_test(line, size)`, its
   line logged whatever it says (below). Phase 3 adds its paths to the same
   setting.

**The link is the check**, as phase 1 had it: `llvm-nm -g --defined-only`
on `d3d8_d3d11.o` against `d3d8_gl.o` still differs by exactly
`xgpu_compile_shader`, `xgpu_link_program`, `xgpu_render_target_find`
(everything this phase adds to the device is static), and
`grep -E '\bgl[A-Z]\w+\('` on `d3d8_d3d11.c` is still 0.

**The statistics line** (`debug.gpu_stats`, every 60 frames) becomes:
`frame <n>: Direct3D 11 clears only; <d> draws, <i> immediate dropped; <c>
clears (<f> by clear calls, <p> drawn), <t> target changes, <a> targets;
<s> presented, <o> not; <r> swap chain resizes; <k> GL stub calls[; <m>
debug layer messages]`, the draws and clears a frame as now, the targets

### The backend: the targets and the clears (`win32_d3d11.c`)

Added to `d3d11_backend.h`, fixed-width integers and `void *` only:

- `uint32_t d3d11_backend_target_create(uint32_t pixel_width, uint32_t
  pixel_height, int depth)`: a `D3D11_TEXTURE2D_DESC` of that size, one mip,
  one sample, `DEFAULT` usage: colour targets `DXGI_FORMAT_B8G8R8A8_UNORM`
  (the Xbox's A8R8G8B8 byte order; `BGRA_SUPPORT` was asked for in phase
  1), bound as `RENDER_TARGET | SHADER_RESOURCE`, with a render target view
  and a shader resource view (the present's sampler reads it now; phase 6's
  draws later); depth targets `DXGI_FORMAT_D24_UNORM_S8_UINT`, bound as
  `DEPTH_STENCIL`, with a depth-stencil view (phase 6 changes the format to
  the typeless one when a draw samples a depth target, if any does). **Cleared
  once when made** (`ClearRenderTargetView` to black with alpha 1, or
  `ClearDepthStencilView` to depth 1 and stencil 0), so a target read before
  anything was drawn into it reads the same on both drivers. Kept in a table
  the handle indexes (1 upward; 0 is none), never freed; the count is for the
  statistics (`uint32_t d3d11_backend_targets_alive(void)`). A creation that
  fails is logged with the `HRESULT`, the size and the kind, and returns 0.
- `void d3d11_backend_targets_set(uint32_t color, uint32_t depth)`:
  `OMSetRenderTargets` with the views (either NULL), and the viewport
  `RSSetViewports` to the whole colour target (or the depth one): the clears
  of this phase set their own scissor, and phase 6's draws set the game's
  viewport at each draw. Remembered, so the clears and the present know what
  is bound.
- `uint32_t d3d11_backend_clear(uint32_t channels, const float color[4],
  float z, uint32_t stencil, const int32_t *rectangles, uint32_t count)`:
  rectangles as `x, y, width, height` in the bound targets' pixels, row 0 at
  the top, already clipped (the device's work above). Returns 1 if the whole
  clear went through clear calls, 2 if any of it was drawn, 0 if nothing was
  bound (the device's statistics count by it). The rule:
  - A colour clear **of all four channels whose one rectangle is the whole
    colour target** is `ClearRenderTargetView`; a depth or stencil clear
    whose rectangle is the whole depth target is `ClearDepthStencilView`
    with the flags asked for. `ID3D11DeviceContext1::ClearView` with
    rectangles exists from the 11.1 runtime, and is not used (Decisions:
    nothing of 11.1; and it is a colour-only call).
  - **Everything else is drawn**: each rectangle a `RSSetScissorRects` and a
    `Draw(3, 0)` of a full-target triangle (the vertex shader from
    `SV_VertexID`, no input layout, no vertex buffer), with a blend state
    whose write mask is the colour channels asked for (none for a depth or
    stencil clear alone; the sixteen masks made the first time each is
    used), a depth-stencil state by (depth asked, stencil asked): depth
    test `ALWAYS` with write on or off, stencil `ALWAYS` with `REPLACE` on
    pass (both faces) and the reference set at the draw, the pixel shader
    writing the colour from a constant buffer and the depth as `SV_Depth`
    (the `z` asked for; when depth is not asked the write is masked by the
    state, so one shader serves), a rasterizer state with the scissor on and
    no culling. The state objects and the constant buffer (`DYNAMIC`, `Map`
    with `DISCARD`, 32 bytes) are the backend's own, made at the first use
    and kept; they are not the game's (phase 5). Nothing is restored after:
    from this phase every state the context holds is the backend's, and
    phase 6's draws set what they need.
- **The built-in shaders**: the clear's vertex and pixel shader and the
  present's (below), HLSL string constants in the backend (`vs_4_0`,
  `ps_4_0`, `D3DCOMPILE_OPTIMIZATION_LEVEL3`), compiled at the first use
  with `D3DCompile` from `d3dcompiler_47.dll`, loaded as the probe loads it
  (`load_compiler`, 656: `LoadLibraryA`, `GetProcAddress`; the `pD3DCompile`
  type from `d3dcompiler.h`). This is the backend's first use of the
  compiler; phase 5 makes the compiler a service and moves the loading
  there. A compile that fails is logged with the compiler's text once, and
  the clears that need it are not drawn (counted as 0: the statistics show
  it); the present without its shaders clears the swap chain's buffer black
  and presents that, so the game still runs and the log says why the window
  is black.
- `int d3d11_backend_target_read(uint32_t handle, void *pixels, size_t
  size)`: a `STAGING` texture of the target's size and format with CPU read
  access, `CopyResource` from the target, `Map` for reading, the rows copied
  out by `RowPitch` (the target's rows are `pixel_width * 4` bytes), `Unmap`;
  the staging texture kept and remade when the size differs (one at a time
  is enough: screenshots and the self-test). 1 on success; 0, logged, on
  anything else (a depth target: not readable this way, and nothing asks).
- `int d3d11_backend_self_test(char *line, size_t line_size)`: the Vulkan
  plan's clears' self-test (its "Phase 2 — summary"): an 8x8 colour target
  and an 8x8 depth target of the backend's own, bound; cleared in full to
  (0.25, 0.5, 0.75, 1.0), depth 0.5, stencil 7; then alpha only (0.5) on the
  left half (a drawn clear); then red only (1.0) with a depth clear to 0.25
  on the top-right quarter (drawn); the colour target read back and every
  texel compared within 1 of 255 with what the NV2A would give (the three
  regions); the depth target checked through the next clear's path only if
  phase 6 adds a depth read-back (it is not read here; the line says so).
  The line: `d3d11: clears self-test: ok (a full clear, alpha only on the
  left half, red only on the top right quarter; 2 partial clears drawn, 1 by
  clear calls)`, or the first texel that differs, with what it holds and what
  it should. The targets are released after; the state objects it made stay
  (they are the clears').
- `int d3d11_backend_lost(void)`: 1 once any call answered
  `DXGI_ERROR_DEVICE_REMOVED` or `DXGI_ERROR_DEVICE_RESET`. The backend logs
  `d3d11: the device was removed (<call>: <hresult>; reason <hresult name>)`
  from `GetDeviceRemovedReason` the first time, and from then on every entry
  point returns at once (0, or -1 from `present`). The debug layer's
  messages are drained once more before the backend stops. `destroy` still
  runs at exit and releases what it has.

### The backend: the swap chain and the present (`win32_d3d11_present.c`)

Copied from the probe's `step_present` (2436–2560: the factory, the
tearing check, the description, `CreateSwapChainForHwnd`,
`MakeWindowAssociation`, `make_view`, 2221) and `resize` (2243–2265), and said so
in the file's header. Phase 0 proved these on the Adreno and on WARP,
through every transition, with the debug layer silent.

- `int d3d11_backend_window_set(void *hwnd, char *line, size_t line_size)`:
  called by the device once after `d3d11_backend_create` succeeds, with
  `platform_video_native_window()` (phase 1 added it; `sdl_platform.c` 769).
  The swap chain's factory is the device's own (`IDXGIDevice` →
  `GetAdapter` → `GetParent` of `IDXGIFactory2`), not phase 1's
  `CreateDXGIFactory1` one (DXGI wants the swap chain made by the factory
  the device came from; the probe does this). `CheckFeatureSupport(DXGI_FEATURE_PRESENT_ALLOW_TEARING)`
  on `IDXGIFactory5` when that interface exists, else no tearing. The
  description as Decisions has it: `FLIP_DISCARD`, two buffers,
  `B8G8R8A8_UNORM`, `DXGI_SCALING_NONE`, no MSAA, `RENDER_TARGET_OUTPUT`,
  width and height 0 (the window's), `ALLOW_TEARING` in the flags when
  supported. Then `MakeWindowAssociation(hwnd, DXGI_MWA_NO_ALT_ENTER |
  DXGI_MWA_NO_WINDOW_CHANGES)`, and the back buffer's render target view.
  The line, logged by the device as the `renderer:` line is: `d3d11: swap
  chain 1280x960, FLIP_DISCARD, 2 buffers, B8G8R8A8_UNORM, tearing allowed`
  (or `tearing not supported`), or `d3d11: no swap chain (<call>: <hresult>)`,
  on which the game runs with the window black and nothing presented (the
  pacing is the stand-in's), as a lost device leaves it.
- `int d3d11_backend_present(uint32_t back_buffer, uint32_t window_width,
  uint32_t window_height, int sync_interval)`:
  1. **The resize.** The window's pixel size, which the device polls each
     frame from `platform_video_drawable_size` (the platform layer handles
     no resize event, and gains none), against the swap chain's: when they
     differ and neither is 0, `OMSetRenderTargets(0, NULL, NULL)`, the view
     released, `Flush`, `ResizeBuffers(0, 0, 0, DXGI_FORMAT_UNKNOWN, flags)`
     with the swap chain's own flags, the view made again; logged as `d3d11:
     swap chain resized 1280x960 to 1600x1000 (<hresult>)` and counted. A
     size of 0 in either axis (minimised) presents nothing and returns 0.
  2. **The letterbox**, as `d3d8_gl.c`'s `Present` works it out (4800–4809)
     from the back buffer's pixel size and the window's: the largest
     rectangle of the back buffer's shape that fits, centred.
  3. **The draw**: the swap chain's view bound, cleared black (alpha 1), the
     viewport set to the letterbox rectangle, the present's pipeline: the
     full-target triangle vertex shader (the same as the clear's, with the
     texture coordinates from `SV_VertexID`), a pixel shader sampling the
     back buffer's shader resource view with a linear-filter, clamp sampler
     (the one sampler state of this phase), the blend state with every
     channel written and no blending, depth off, `Draw(3, 0)`. Row 0 of the
     target is the top of the picture; no flip, as "Clip space" says. The
     back buffer's view must not be bound as a target while it is sampled:
     `targets_set(0, 0)` first (the device binds again at the next clear or
     draw).
  4. **The marker** (`debug.d3d11_present_marker`): after the draw, a red
     square (16 by 16 pixels) at the letterbox rectangle's top-left corner
     and a green one at its top-right, through the clear's drawn path
     (scissor, the clear's shaders, all channels), so a screenshot of the
     window shows the letterbox's edges and the picture's orientation. The
     setting is read when `config_changes()` moves, as the device reads its
     own.
  5. **`Present(sync_interval, flags)`** with `DXGI_PRESENT_ALLOW_TEARING`
     when the interval is 0 and tearing is supported (the probe's rule). The
     debug layer's messages are drained by the device as before (phase 1's
     `drain_debug` at `Present`). `S_OK`: return 1. `DXGI_STATUS_OCCLUDED`
     (minimised, or covered): return 0 (the device paces by the stand-in,
     so the game does not spin, as the probe slept 16 ms). `DXGI_ERROR_DEVICE_REMOVED`
     or `DEVICE_RESET`: the lost path above, return -1. Anything else: logged
     once per distinct result with its name (`hr_text`), return 0.
- **Fullscreen is SDL's alone** (Decisions): the swap chain never calls
  `SetFullscreenState`; F11 (borderless) and `display.mode`'s exclusive
  fullscreen change the window's pixel size, which the resize above follows.
  Alt+Enter does nothing (`DXGI_MWA_NO_ALT_ENTER`; phase 0 saw it).
- A display change (`SDL_EVENT_WINDOW_DISPLAY_CHANGED`) needs nothing of the
  swap chain in the flip model; the pixel size, if it changes, is followed as
  above. The stand-in pacing's refresh rate is read when a setting changes
  (phase 1); a window moved to a display of another refresh rate while vsync
  is on is paced by the present's interval, which follows the display, so
  the stand-in's stale rate matters only to frames nothing presents.
- `d3d11_backend_destroy` releases the present's objects first (the view,
  the swap chain, the factory, the sampler and the shaders), then the targets
  and the clears' objects, then what phase 1 released; the live-object report
  with the layer on should again name the device's own objects only.

Vulkan phase; the user may know a scene that clears alpha only (the fog
screen) and can say so for phase 6.

## Phase 3 — the game's memory in Direct3D buffers

How a draw's data reaches the GPU, before any draw exists: the stream ring,
the index ring, the mirror and immediate mode, with a self-test. The Vulkan
plan's phase 3 is the model for the self-test; the design is `d3d8_gl.c`'s,
which this phase translates rather than replaces.

- **The stream and index rings**: `DYNAMIC` buffers of the OpenGL build's
  sizes, `Map` with no-overwrite and `DISCARD` at the wrap, the way the
  OpenGL renderer orphans (`stream_reserve`: a draw's streams reserved at
  once, so the wrap never splits them).
- **The mirror** (`d3d8_gl.c`, "the contiguous window in GL buffers"): one
  `DEFAULT` buffer per 4 MB segment, made when first needed, pages
  copied through a ring of `STAGING` buffers (`Map`, then
  `CopySubresourceRegion` into the segment; see "Decisions") when absent or stale by
  `memory_watch`'s generations, the volatile-page rule as it is. The
  generation bookkeeping stays in the device half; the backend only copies
  ranges into segments.
- **Immediate mode's vertices** and **quad lists' indices** as `d3d8_gl.c`
  makes them, into the rings.
- **The self-test** (`debug.d3d11_self_test`): a triangle from each path
  (ring, mirror, immediate), the buffer rewritten in place between two
  draws, drawn into a small target of its own with a built-in pipeline,
  read back: each colour as expected proves the copy was made at the draw.

**Done when:** the self-test says `ok` for every path on the GPU and on
WARP; `IsBusy`, the locks and `BlockUntilNotBusy` unchanged; audited and
committed.

## Phase 4 — HLSL

The two generators as copies emitting HLSL, the header that fixes the
constant buffers' layout, the key made at each draw, a dump, and the proof
on this PC that every shader of the game's corpus compiles and says the same
as its GLSL twin. The Vulkan plan's phase 4 is the model; what differs is
the dialect.

- **Constant buffers**, every member a `float4` or an array of them, every
  member with `packoffset` from `hlsl_shaders.h`'s `#define`s, the C
  structures' `offsetof` checked against the same `#define`s at compile
  time: the vertex constants `c[192]`; the vertex parameters (viewport
  scale and offset, the screen offset; no point size); the pixel
  parameters (the combiner constants, fog, the alpha reference, the bump
  matrices and luminance, the texture scales). The samplers' LOD bias is
  the sampler's.
- **Semantics between the stages**: the nine interface values as
  `TEXCOORD0` to `TEXCOORD8` in a fixed order, every vertex shader writing
  all nine and every pixel shader declaring all nine, so any pair links
  and each stage is cached apart; the position `SV_Position` (`precise` if
  phase 0 found it accepted); the pixel output `SV_Target`. Vertex inputs
  by `TEXCOORD0` to `TEXCOORD15` with the input layout naming them, the
  sixteen declared as now (an attribute the declaration does not feed comes
  from a stride-0 slot holding its current value, as the Vulkan plan does).
- **The dialect**: `discard`, `lerp`, `frac`, `fmod`, `Sample` on a
  `Texture2D`/`Texture3D`/`TextureCube` with its `SamplerState`, `uint` bit
  operations for `NORMPACKED3`, the ES-only branches dropped, no atomic
  counter (`count_samples` is 0: queries). The clip space is the desktop
  branch's as it is (above). Everything else line for line: the instruction
  decoding, the combiners, fog, the alpha test, alpha kill, colour sign,
  `coverage_alpha`, per-pixel lighting, the `debug.gpu_debug_*` settings.
- **The key at each draw** (`pixel_key_make`, as the Vulkan plan's) and a
  dump (`debug.gpu_dump_shaders`): each shader's HLSL and its GLSL twin.
- **The check**, `tools/d3d11_shader_check.py`: loads `d3dcompiler_47.dll`
  with `ctypes` and compiles every dumped shader, reports failures with the
  compiler's text, and diffs each HLSL shader against its GLSL twin with the
  dialect's changes applied and whitespace normalised: a shader that
  compiles and draws black is what this exists to catch. The corpus: the
  menus and the first map's opening, cinematic and play, collected by the
  OpenGL executable's dump and by the Direct3D one's keys.

**Done when:** every shader of the corpus compiles on this PC, the
comparison finds nothing, the key fields vary as a real corpus's do; the
numbers in "Progress"; audited and committed.

## Phase 5 — shaders and state objects

What a draw binds, made once and kept.

- **The shader service**: a shader known by a 64-bit hash of the generator
  version and its program and mask (vertex) or its key (pixel); the
  bytecode cache on disk (`%LOCALAPPDATA%\halo\shaders\<generator
  version>-<compiler version>\`, one file a shader with a header and a CRC,
  written as `.tmp` and renamed; other versions' folders removed at
  start); `D3DCompile` at the draw for a shader not in the cache, the
  shader object made from the bytecode; a failed compile logged once with
  the compiler's text and the HLSL written beside the log for the check
  script. The compile thread, with draws skipped, only if phase 0's
  numbers ask for it.
- **Input layouts** by (vertex declaration, vertex shader's bytecode), from
  `setup_streams`' and `attribute_format`'s decisions mapped to DXGI
  formats once, in a table.
- **State objects** by hash: blend (the factors, the ops, the write mask;
  the blend constant set at the draw), depth-stencil (test, write, compare,
  the stencil ops with both faces the same; reference at the draw),
  rasterizer (cull, front face, fill, the z bias as `DepthBias` and
  `SlopeScaledDepthBias`, scissor on), samplers (filters, address modes,
  the border colour, LOD bias, anisotropy). The Xbox's enumerants are
  OpenGL's; `d3d8_gl.c`'s mapping is the reference for the table, entry by
  entry.
- The statistics line gains: shaders from the cache, compiled, failed;
  layouts and state objects alive; the cache's size.

**Done when:** a second start compiles nothing; a broken cache file is
replaced, not fatal; the menus' and a map's shaders all made with the state
objects counted and stable; audited and committed.

## How this plan is worked

What made the deko3d and Vulkan plans go well, kept here on purpose:

- **Each phase is written out in detail before it is handed over**, with its
  files, its steps, how to test it on this PC and what counts as done. The
  detailed phase is written so that an agent that has not seen the work so
  far can pick it up: it names what to read first, in what order.
- **Each phase goes to an agent with a hand-off prompt**, and comes back
  for an audit: the code against the source and the Direct3D 11
  documentation, the "Progress" entry against what was asked, before the
  commit.
- **Each step is tried on this PC before the next starts**, on the Adreno
  and on WARP. A step that is "done in the tree" and not seen on the screen
  is not done. Screenshots are the evidence: the same scene under the
  OpenGL executable and the Direct3D one, side by side.
- **Every result goes into "Progress"** with what shows it: what was seen,
  what the log said, which adapter. "Progress" is newest first.
- **Work is audited against the source, not against its own description,**
  before it is committed.
- **Diagnostics come before the feature**: the statistics line, the debug
  layer's messages, device-removed handling and screenshots are in from
  phase 2, because a silently dropped draw costs hours without them.
- **The OpenGL renderer stays untouched**, so the comparison in phase 7 is
  against something that does not move, and a player always has a fallback.
- The work is on the `d3d11-backend` branch, from `main`.

### Phase 1: deviations from the spec

Everything phase 1 did differently from the "Phase 1 — the Direct3D executable" section, or beyond it.

**The device**

1. **The backend is not destroyed from `D3DDevice_Release`**, only by the `atexit` handler. The game
   makes the device, presents once and releases it in `rasterizer_preinitialize`
   (`rasterizer_xbox.c` 1950), then makes it again; a destroy there would leave the game with no device.
   `D3DDevice_Release` is `d3d8_gl.c`'s, byte for byte. Every exit seen (the close button, the menu's
   quit) goes through `exit()`, so the handler runs, and its line is in every log.
2. **The draws are counted as asked for**: `DrawVertices` and `DrawIndexedVertices` count one with
   vertices (and indices), `End` one with vertices, `Clear` every call, whatever the backend's state.
   `d3d8_gl.c` counts a draw only once its program is made. The line says "asked for".
3. **The statistics line** gives the draws a frame as `d3d8_gl.c`'s does (`stats` over the 60 frames),
   the GL stub calls since the self-test (the self-test's own call subtracted), and `; <n> debug layer
   messages` (since the last line) only when `debug.d3d11_debug` is set: the device asks no more of the
   backend than the three functions.
4. **The frame is paced whenever there is a window**, the backend made or not, so a machine without a
   device does not spin. `d3d8_gl.c` swaps only with its context.
5. **The menus' pointer works with the window** (`window_ready`), not with the backend, and takes the back
   buffer's pixels from `back_buffer_pixels` (the surface's size at the screen's scale), which is what
   `render_target_get` gave `ui_point_from_window_on`; `render_target_get` itself is gone with the
   targets.
6. **Anti-aliasing**: `anti_aliasing_prepare` is gone (it built the passes and read the GPU's sample
   count); the setting is still read and logged as before. `maximum_target_size` stays 0, so `ssaa2x`
   draws at the screen's scale until phase 6 asks the backend.
7. **The visibility tests' begin and end** keep only `visibility_test_active`, behind `backend_ready`
   as `d3d8_gl.c`'s are behind `gl_ready`. `trace_draw` is gone (it asks `xgpu_render_target_find`);
   `trace_frame` stays for `SetRenderTarget`'s and `Clear`'s trace lines.
8. **The stub self-test** fails loudly by a log line and by not using the device (`backend_ready` false),
   not by stopping the game.

**The backend**

9. **The info queue is first drained at the first `Present`**, not at creation, so that the `renderer:`
   line, which the device logs, comes first; `d3d11_backend_destroy` drains what is left before the
   live-object report. A second `d3d11_backend_create` returns the device made before, with a line that
   says so.
10. **Below 11_0** the adapter is asked again at 10_1 and 10_0 only when the first answer was
    `DXGI_ERROR_UNSUPPORTED` or `E_INVALIDARG`, so that another failure (a debug layer that fails in
    another way) is not named a feature level.
11. **The backend logs `d3d11: device released`** at the end of `d3d11_backend_destroy`, the "destroy
    line" the testing asks for, and the live objects' count as `d3d11: the live objects at the end, from
    the debug layer: <n> messages`.

**The platform layer, the stubs and the build**

12. **The no-context window is a function of its own**, `platform_video_initialize_without_gl`, which
    `platform_video_initialize` calls first when the flag is set, rather than conditions through the
    OpenGL path: the desktop window's lines are repeated without `SDL_WINDOW_OPENGL` (fullscreen kind,
    event thread, mouse capture). The OpenGL path's lines are untouched.
13. **The two settings rows are behind `#ifdef _WIN32`** (the existing `_platform_windows` row,
    `crash_reports.upload`, is not), so the Linux and Android tables do not change at all.
14. **`gl_stubs.c` also defines `gl_functions_load`**: `sdl_platform.c` references it on its OpenGL path,
    which the link needs, and here it logs a line and fails.
15. **A stub's first caller is logged with its offset into the executable** (`halo_d3d11.exe+0x...`,
    from `__ImageBase`) beside the address, because the executable is relocated (ASLR); the offset is
    what `llvm-symbolizer --relative-address` takes.
16. **`emit()` builds the Direct3D executable itself** when given its path (and returns its objects): the
    Direct3D units need the same flags `emit()` builds, and the training build of `--pgo=train` simply
    does not ask for it.
17. **The object check's method** (above): both trees built with `-ffile-prefix-map` through
    `CCC_OVERRIDE_OPTIONS`, and three more objects than the two named differ, each explained.
    `win32_crash.o` is the phase's own change.

**Testing**

    the user was using the PC; the window is what the captures and the title bar need. With nothing
    drawn the resolution costs nothing, and the game's width is 640 instead of 852. The sound was at
    `audio.volume` 0.05.
19. **The cryo room was told from the statistics and the game's clock**, not seen: the window is black,

20. **The menus were driven by keys** sent to the window (`keybd_event`, arrow keys with the extended-key

- **The swap chain and fullscreen**: proposed row:

  | Presenting | **`DXGI_SWAP_EFFECT_FLIP_DISCARD`, two buffers, `B8G8R8A8_UNORM`, `DXGI_SCALING_NONE`**, made on SDL's `HWND` with `MakeWindowAssociation(DXGI_MWA_NO_ALT_ENTER \| DXGI_MWA_NO_WINDOW_CHANGES)`. With `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` when the factory says it is supported (it is on both drivers here), and `DXGI_PRESENT_ALLOW_TEARING` with sync interval 0 when `display.vsync` is false. **Fullscreen is SDL's alone** (borderless, and SDL's display-mode fullscreen); DXGI's `SetFullscreenState` is never used. The same flags go to `ResizeBuffers` on every `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED`. Every transition presented again within 110 ms on both drivers, and minimised windows present `S_OK`, so there is no occluded state to handle. |
- **Feature level**: proposed row:

  | Feature level | **11_0 required, nothing of 11_1 used.** The Adreno and WARP both offer 11_1, but 11_0 has everything the renderer relies on (BC1 to BC3, exact occlusion queries, the formats in the table above), and keeping to 11_0 keeps more of the testers' GPUs. |
- **If the emulated process does not reach the Adreno**: it does (the first finding), so the plan
  goes on as written and nothing replaces it.

Two findings bear on rows not marked (to confirm). The user took the first (the mirror through `STAGING` buffers, now in "Decisions" and phase 3); the second needs no change:

- **The game's memory.** `UpdateSubresource` by page costs 4 ms of CPU a frame for a whole 4 MB
  segment on the Adreno. Copying the same pages into a STAGING buffer and then
  `CopySubresourceRegion` costs 1.7 ms. The a10 scene mirrors 5–6 MB a frame under OpenGL. Phase 3
  could take the staging path for the mirror's uploads, with a ring of staging buffers, one a frame
  in flight. The rewrite test passes on both paths and both drivers.
- **Occlusion queries on WARP** answer only after a flush. The renderer's `Present` flushes every
  frame, so phase 6's "never a wait" is safe, but the latency on WARP is one frame plus the flush.

### Phase 0: deviations from the spec

Everything phase 0 did differently from the "Phase 0 — spike" section, or beyond it. **The user
accepted all of them.**

**The build**

1. **The probe is large-address-aware** (`/LARGEADDRESSAWARE`, as `halo.exe` is), so that its
   address-space figures are the game's (4 GB, not 2 GB). The spec lists only `/SUBSYSTEM:CONSOLE`.
2. **The build stamp reuses `tools/android_build_stamp.py`** (unchanged; it takes the header's
   path), through a rule of its own, `windows_build_stamp`, run at every build and restat. It
   writes `build/windows/d3d11_probe_build.h`. The header still says it comes from the Android
   script, and the macro is the Android probe's `HALO_PROBE_BUILD`.
3. **`d3dcompiler_47.dll` is loaded with `LoadLibrary`**, not linked through `d3dcompiler.lib`, so
   that the report can give the DLL's load time, path and version. The Decisions table allows
   either. The link adds `dxguid.lib` (the interface IDs), `advapi32.lib` (the processor's name from
   the registry) and `version.lib` (the DLL's version).
4. **The reports' build is `d071462e+changes`**: they were made before the probe was committed.

**The probe's steps**

5. **The order of the steps is `caps, compile, memory, queries, present`.** The spec's list is
   `caps,present,compile,memory,queries` "in that order", but it also says that `present` runs last.
   `compile` runs right after `caps`, so that its first compile is the process's first.
6. **`--quiet`** (not in the spec): `present` plays no tone. The user asked for no sound, so every
   run was made with it. The tone itself is written but not tried.
7. **`present` ends on Escape twice in a row** (an Escape from fullscreen returns to the window; a
   second one ends the step), on B, on the window being closed, or after 120 s without input. A
   minimise or restore counts as input. Each window event (minimised, restored, fullscreen in and
   out) is reported with the time to the next `S_OK` present.
8. **`present`'s pacing keeps at most 65,536 intervals in each 10 s window**, so the sync-0 runs
   on the Adreno (about 9,000 presents a second) report the first 65,536 of each window.
9. **`ResizeBuffers` is given the swap chain's own flags** (`ALLOW_TEARING` where the swap chain
   has it), not 0, because DXGI requires the same flags.
10. **`compile` measures more than the spec asks**: `D3DCOMPILE_OPTIMIZATION_LEVEL1` and
    `D3DCOMPILE_SKIP_OPTIMIZATION` at 4_0, for the record. The `precise` test is a small built-in
    vertex shader in three forms (`precise` on the output member, on a local, and
    `IEEE_STRICTNESS` without `precise`), not one of the converted shaders.
11. **The shaders were converted by a script, not by hand.** The script does only the changes the
    spec lists, and the bodies are kept as they were. The loose `float` uniforms (`point_size`,
    `screen_offset`, `alpha_reference`) go into one `float4 loose_floats` with `#define`s. The
    interface values become `static` globals, which a `main` wrapper fills from the input struct
    and copies to the output struct. `main` becomes `glsl_main`, and `gl_PointSize` is dropped. A
    one-argument `vecN(x)` becomes a cast. The pixel shader's input struct starts with
    `SV_Position`, as the vertex shader's output does. The files are named `vs_large`,
    `vs_typical`, `ps_large`, `ps_typical`, `vs_pass` and `ps_pass`, and each names the dump file
    and the build it came from. The script is not in the tree. All six compiled on the first try.
12. **`memory`** draws one triangle from each 64 KB piece of the ring and from each updated page of
    the mirror, into a 16x16 target. Frames are paced like a swap chain's: at most three in
    flight, by event queries, and a `Flush` at the end of each frame stands in for the present. The
    mirror's STAGING comparison uses a ring of three staging buffers. The rewrite test has four
    paths: the ring by appending with `NO_OVERWRITE`, the ring by `DISCARD`,
    `UpdateSubresource`, and STAGING plus `CopySubresourceRegion`. The address space is also
    reported between the sub-steps.
13. **`queries`**: the 64 queries are issued in the first frame and polled in each later frame of
    16.7 ms, up to 180 frames, with one draw a frame as the frame's other work. A query that never
    answers is checked once after a flush and a wait. All 64 squares are drawn at the target's
    corner: they overlap, which does not matter to a query's count.
14. **Timing**: thread CPU time from `GetThreadTimes` moves in steps of 15.6 ms on this machine.
    The probe reports the step (`timing.thread_cpu_step`) and keeps the figures, but they mean
    nothing below that. Wall time is the figure to read.

**Testing**

15. **The debug layer's runs came later**, after the user installed the feature and restarted
    (the entry above). The first four runs have no layer.
16. **`present` was driven by the agent**, by SendKeys and window calls (`SetWindowPos` for the
    resize by the edge, `ShowWindow` to minimise and restore). The user was working on the PC at
    the same time, so in the two Adreno runs some of the user's keys reached the probe's window
    (they are in the reports as `present.key` lines: `M I S M O Return`, `Left Windows`, `V E
    Space`). The one "looks right" answer comes from that, and nobody judged the picture.
    Screenshots of the window by screen capture showed other windows on top and were deleted.
    There was no gamepad.
17. **The baseline**: the frame rates come from the `gpu_stats` lines (every 60 frames) timed as
    they reached `halo.log`, interpolated to whole seconds, because the line has no time of its

    scenes were started from the telnet console (`map_name a10`) with the settings given above.
